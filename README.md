# devenv

Окружение для разработки в rootless Podman: Ubuntu, zsh, Neovim, Claude Code,
Codex CLI, pi и мои dotfiles. Контейнер ограничивает доступ к хосту, но видит
смонтированный проект, данные агентов и их credentials. Это не изоляция агентов
друг от друга.

## Запуск

Нужны Python 3.11+, [just](https://github.com/casey/just), rootless Podman и
Docker Compose v2 через сокет Podman:

```sh
systemctl --user enable --now podman.socket
```

Один раз из клона этого репо (нужен import, не симлинк):

```sh
echo "import '$PWD/justfile'" > ~/.justfile     # локальные compose-файлы
# Или compose из main на GitHub, рецепты/скрипты подготовки — из этого клона:
echo "import '$PWD/remote.just'" > ~/.justfile
```

Перед первым запуском выполните миграцию ниже или дождитесь синхронизации
конфигурации. `just` проверяет её наличие и не создаёт пустые настройки поверх
ещё не приехавших файлов.

| Команда | Что делает |
|---|---|
| `just` | зайти в контейнер; удаляется, когда выходит последний шелл |
| `just up` / `just down` | поднять в фоне / удалить |
| `just pull` | скачать свежий образ; нужен перезапуск контейнера |
| `just build` | собрать образ с локальными dotfiles |
| `just migrate-agents` | скопировать данные прежних схем в единое хранилище |
| `just agents-snapshot` | сделать переносимые снимки SQLite Codex после завершения клиентов |
| `just agents-restore` | восстановить SQLite из синхронизированных снимков |
| `just agent <task>` | агент в worktree `<проект>.agent/<task>` на ветке `<task>` |
| `just agent-shell <task>` / `just agent-down <task>` | войти / удалить контейнер задачи |

Проект монтируется по тому же абсолютному пути, что и на хосте.
`compose.local.yaml` в корне проекта подключается автоматически. На сервере
с видеокартой `just` добавляет `compose.gpu.yaml`.

Без just, из клона devenv, сначала подготовьте хранилище и общие тома:

```sh
python3 scripts/agent_storage.py init
podman volume create devenv-cache
podman volume create devenv-mason
```

Затем из проекта:

```sh
podman compose -p "${PWD##*/}" -f 'https://github.com/gelerum/devenv.git#main:compose.base.yaml' up -d
podman compose -p "${PWD##*/}" -f 'https://github.com/gelerum/devenv.git#main:compose.base.yaml' exec dev zsh
```

## Единое хранилище агентов

Общий корень на хосте — **`~/.config/devenv/agents/`**:

```text
agents/
├── claude/
│   ├── config/   # настройки, синхронизировать
│   ├── data/     # история и память, синхронизировать
│   └── auth/     # локальный вход, НЕ синхронизировать
├── codex/
│   ├── config/
│   ├── data/
│   └── auth/
└── pi/
    ├── config/
    ├── data/
    └── auth/
```

В следующей таблице пути относительны папке соответствующего агента:

| Данные | Claude Code | Codex CLI | pi |
|---|---|---|---|
| Настройки | `config/settings.json` | `config/config.toml` | `config/settings.json`, `config/models.json` |
| Авторизация | `auth/credentials.json`, необязательный `auth/claude.env` | `auth/auth.json` | `auth/auth.json` |
| История и сессии | `data/projects/`, `data/history.jsonl` | `data/sessions/`, `data/archived_sessions/`, `data/history.jsonl` | `data/sessions/`, `data/subagents/` |
| Память | `data/projects/<project>/memory/` | `data/memories/` и SQLite-снимки | `data/memory/` |
| Дополнительное переносимое состояние | — | `data/session_index.jsonl`, `data/sqlite-snapshot/` | — |

Native-пути внутри контейнера остаются прежними: `~/.claude`, `~/.codex`,
`~/.pi/agent`. Их целиком с хоста **не монтируем**. Каталоги истории и памяти
подключаются напрямую; настройки и отдельные файлы истории связываются
с каталогами `/run/agents/`. Замена конфигов через Syncthing/rename видна контейнеру.
Credentials работают иначе: клиент получает приватную копию, чтобы запоздавший
refresh одного контейнера не восстановил логин после logout в другом.

Лаунчеры `claude`, `codex`, `pi` публикуют изменённые credentials и заменённые
клиентом файлы при выходе. Межконтейнерный lock и версии состояния защищают от
устаревшей записи; logout оставляет tombstone. Конфликтующая версия не затирает
новую: она сохраняется в локальном `auth/conflicts/`, с предупреждением в stderr.
Эти копии тоже могут содержать секреты; после разбора удалите ненужные вручную.
Изменения credentials другого контейнера подхватываются при следующем запуске,
не во время текущей сессии. Если параллельные OAuth refresh сделали токен сессии
неактуальным, перезапустите клиент; иногда потребуется повторный вход.

В одном контейнере разрешён один активный экземпляр каждого клиента. Для
параллельных задач используйте разные контейнеры/worktree. Используйте обычные
команды из PATH, не обходите лаунчеры через native-бинарники. После SIGKILL и
**удаления** контейнера непубликованные изменения могут потеряться; при рестарте
того же контейнера они восстанавливаются с проверкой версий. Завершайте клиенты
штатно перед переключением устройства. Напрямую смонтированные сессии сохраняются
без ожидания выхода клиента.

Расширения, темы и агенты pi, навыки Claude остаются в образе/dotfiles.
У Claude `config/settings.json` заменяет ссылку из Stow при старте контейнера,
не меняя сам dotfiles; managed settings образа продолжают применяться. `.claude.json`
с доверием к проекту и onboarding остаётся внутри контейнера, не синхронизируется.
Сохраняется файловая OAuth-авторизация Claude; OS keyring с хоста не подключается.
Файлы OAuth сторонних MCP-серверов отдельно в эту схему не включены.

### Вход и телеметрия

На каждом устройстве войдите отдельно: `claude`, `codex login --device-auth`,
`pi` → `/login`. Вход сохраняется вне контейнера и переживает его пересоздание.
Для Claude можно вместо OAuth использовать локальный
`agents/claude/auth/claude.env` с переменными окружения. Этот файл читается Compose
при создании контейнера; изменения требуют пересоздания.

В новом конфиге Codex миграция отключает analytics, feedback и OTEL exporters.
Существующий `config.toml` не меняется: при необходимости добавьте вручную:

```toml
cli_auth_credentials_store = "file"

[analytics]
enabled = false
[feedback]
enabled = false
[otel]
exporter = "none"
metrics_exporter = "none"
trace_exporter = "none"
```

У Claude необязательный трафик отключён managed settings образа, у pi задано
`PI_TELEMETRY=0`. Это настройки клиентов, а не запрет исходящей сети.
Ограничение mounts само по себе не отключает телеметрию.

Рефлексия памяти pi при выходе использует локальную модель
`calculation/qwen3.6-35b-a3b`, зарегистрированную в pi `models.json`.
Основная модель чата остаётся выбранной в pi. Для другой модели рефлексии задайте
`PI_MEMORY_REFLECT_MODEL=provider/model` на хосте перед запуском контейнера.
Изменение применяется после пересоздания контейнера.

### Два устройства: синхронизация и переход

1. Подключите к Syncthing **шесть папок**: `config/` и `data/` каждого агента.
   **Не подключайте корень `agents/` целиком и не синхронизируйте `auth/`.**
2. На первом устройстве штатно завершите все клиенты, затем выполните
   `just agents-snapshot`. Это сохраняет SQLite-память и индексы Codex без
   пересылки работающих БД и WAL-файлов. БД `logs_*` в снимки не входят.
3. Дождитесь окончания синхронизации всех шести папок на втором устройстве.
4. До запуска Codex на втором устройстве выполните `just agents-restore`.
   Список файлов и SHA256 в `manifest.json` проверяются до изменения локальных
   баз: неполная синхронизация прерывает restore. Предыдущие локальные базы
   сохраняются в `before-restore-*` рядом с ними; базы, отсутствующие в снимке,
   убираются из рабочего набора, чтобы не смешивать состояние двух устройств.
   После этого запускайте агентов.
5. При обратном переходе повторите snapshot → дождаться sync → restore.

Рабочие SQLite-базы Codex лежат **вне синхронизации**, на хосте в
`~/.local/share/devenv/agents/codex/sqlite/`; в контейнере —
`~/.local/state/codex/sqlite/` через `CODEX_SQLITE_HOME`. Удалите явный
`sqlite_home` из конфигурации: он имеет приоритет над переменной. Подготовка
и запуск Codex отвергают этот ключ и хранилища credentials `keyring`/`auto`,
чтобы настройки не обходили сохранение локальных баз и файловой авторизации.
Snapshot/restore отказываются работать при запущенном через наш лаунчер Codex;
не запускайте native-бинарники в обход него. Снимки не создаются автоматически.
В первый раз, пока Codex ещё не создал БД, переносить SQLite нечего.

Не продолжайте одну сессию и не редактируйте общую память/настройки одновременно
на двух устройствах. Разрешайте `.sync-conflict` вручную; Syncthing не объединяет
содержимое JSONL/JSON/Markdown семантически. После внешнего изменения настроек
перезапустите клиент или перечитайте настройки; pi поддерживает `/reload`.
Одинаковые абсолютные пути проектов на обоих устройствах упрощают поиск сессий
и проектной памяти; pi-сессию также можно открыть явно: `pi --session <файл>`.

**Конфиги тоже могут содержать секреты:** не храните API-ключи прямо в
`models.json`/`config.toml`, используйте переменные окружения или локальное auth.
История и память содержат приватные данные; синхронизируйте только между
доверенными устройствами. Не добавляйте всё хранилище в Git.
Кеш каталога моделей pi, зависимости расширений, кеши языков и `/nix` не синхронизируйте.

### Миграция существующих данных

Остановите клиентов и контейнеры на устройстве, приостановите прежние Syncthing-
папки истории/памяти и затем из обновлённого клона выполните:

```sh
just migrate-agents
# Без just:
python3 scripts/agent_storage.py migrate --dotfiles ../dotfiles
```

Миграция копирует выбранные файлы из прежних `~/.claude`, `~/.pi/agent`,
`~/.config/devenv/pi`, `~/.codex`, `~/.config/devenv/codex` и
`~/.local/share/devenv/codex`. Локальные credentials копируются в `auth/`,
старые SQLite — в локальный runtime, а не в синхронизируемое `data/`.
Оригиналы не удаляются. Различающиеся файлы, претендующие на один destination,
вызывают ошибку **до копирования**: выберите актуальную версию вручную.
Повторный запуск после изменения новых файлов тоже может обнаружить конфликт.

Настройки Claude берутся из хостового `~/.claude/settings.json`, иначе — из
переданного локального dotfiles. Если ни того, ни другого нет, создаётся `{}`.
Новый Codex получает минимальный конфиг с отключённой телеметрией. У pi миграция
не генерирует настройки: нужны старые или уже синхронизированные обычные
`settings.json` и `models.json`. Отсутствие этих файлов завершает подготовку
ошибкой; уже скопированные файлы и оригиналы при этом остаются на месте.

На втором устройстве сначала синхронизируйте `config/` и `data/`. Если там нет
старых данных, `just` создаст локальные auth-каталоги, после чего войдите заново.
Если там тоже есть старая история, выполните миграцию **до объединения** с первым
устройством; конфликты общей истории и конфигов разрешайте вручную.

После подготовки нужен образ с новым entrypoint и лаунчерами: `just pull` после
публикации CI, затем `just down` и `just` (или локальный `just build`). Старые
запущенные контейнеры не получают новые mounts автоматически. Не удаляйте старые
папки до проверки входа, сессий и памяти. Если нужна память Codex на втором
устройстве сразу после миграции, выполните snapshot/sync/restore до запуска там.

## Общие инструкции Claude Code и Codex

Рекомендуемый общий файл проекта — `AGENTS.md`: Codex читает его напрямую.
Claude Code начиная с 2.1.277 тоже поддерживает его, но по умолчанию только когда
в текущей папке и выше нет `CLAUDE.md`/`CLAUDE.local.md` (включая `.claude/CLAUDE.md`).
Для предсказуемой работы оставьте в соседнем `CLAUDE.md` импорт:

```markdown
@AGENTS.md
```

Для вложенных инструкций используйте такую же пару файлов в подпапках.
Альтернатива на Linux — симлинк `CLAUDE.md -> AGENTS.md`.
Если основным остаётся `CLAUDE.md`, добавьте в конфиг Codex:

```toml
project_doc_fallback_filenames = ["CLAUDE.md"]
```

Он применяется, если в каталоге нет непустого `AGENTS.override.md`/`AGENTS.md`.
Импорты `@...` — механизм Claude, не рассчитывайте на их раскрытие в Codex.
Глобальные инструкции, если нужны, подключайте отдельно; эта схема относится
к файлам внутри проекта.

Документация: [Codex AGENTS.md](https://developers.openai.com/codex/guides/agents-md),
[Claude memory](https://code.claude.com/docs/en/memory#agentsmd).

## Свой образ и языки

`just build` использует локальные `../dotfiles` или `DEVENV_DOTFILES`, включая
незакоммиченные изменения. Если папки нет, dotfiles клонируются на `DOTFILES_REF`.
Тег тот же, что у CI; `just pull` вернёт образ из CI. Бинарники скачиваются из сети.

| Язык | Файл версии | Команда |
|---|---|---|
| Go | `go.mod` | `go ...` |
| Rust | `rust-toolchain.toml` | `cargo ...` |
| Python | `.python-version`, `pyproject.toml` | `uv sync`, `uv run ...` |
| conda | `environment.yml` | `conda env create -f environment.yml` |
| Nix | `flake.nix` | `nix develop` |

Mason ставит LSP и форматтеры при первом запуске Neovim;
`DEVENV_LANGS="go python"` ограничивает языки. Общие локальные хранилища:

- `devenv-cache` — языки, окружения conda и кеши пакетов;
- `devenv-mason` — LSP и форматтеры;
- `~/.local/share/devenv/nix` — `/nix` контейнера, отдельно от хостового.

Образ: `ghcr.io/gelerum/devenv`. CI собирает после push сюда/в dotfiles и каждый
понедельник с обновлением версий через `scripts/update-versions.sh all`.
Версии и SHA256 — в `Dockerfile`; закрепить образ можно в `.env`:
`DEVENV_IMAGE=ghcr.io/gelerum/devenv:sha-<коммит>`.

Проверки: `python3 -m unittest discover -s tests -v` и
`shellcheck entrypoint.sh agent-launcher.sh scripts/update-versions.sh`.
